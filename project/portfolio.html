This Portfolio

The site you are reading. A React single page app deployed to GitHub Pages, with a projects section that reads its own statistics and documentation from the GitHub API at runtime.

Author: Mert İlhan (Mert Ilhan) · Category: Web · Technologies: React, React Router, Bootstrap, GitHub API, GitHub Pages

View This Portfolio source code on GitHub

Built on Create React App with React 17 and React Router 6. The interesting parts are not the framework choices but the constraints: it is a client side app served from a static host under a subpath, and its content comes from an API with a hard rate limit and no authentication. Most of the engineering below is about those two facts.

Built with

  • React (17): Component model and state
  • React Router (6): Client side routing, mounted under a basename for the GitHub Pages subpath
  • Create React App (5): Build pipeline — webpack 5, Babel and the dev server with hot reload
  • React Bootstrap (2): Responsive grid and card primitives over Bootstrap 5
  • react-tsparticles: The animated starfield behind every page
  • typewriter-effect: Rotating role titles in the home page headline
  • react-parallax-tilt: Tilt on the avatar that follows the cursor
  • react-github-calendar: The contribution heatmap in the Days I Code section
  • react-icons (4): Simple Icons, Ant Design and Devicons sets — every logo on the site is an SVG component, not an image
  • GitHub REST API: Repository statistics and README HTML, fetched at runtime and cached for an hour
  • gh-pages: Publishes the production build to the gh-pages branch in one command

Routing on a static host

GitHub Pages serves files, not routes, so a refresh on /project/libft would normally 404. Each route is pre-rendered to its own static HTML file at build time with dedicated metadata and structured data, while a 404.html fallback preserves unknown deep links back to the client router.

Live data with a hard rate limit

The unauthenticated GitHub API allows sixty requests an hour per address. All repository statistics come from a single call that is indexed by name and cached in sessionStorage for an hour, so the list page and every detail page share one request instead of making their own. Browsing four pages costs three requests, and they are all README fetches.

Documentation rendered by GitHub

Each detail page asks the API for the repository README as rendered HTML rather than raw markdown. No markdown parser is bundled, image paths arrive already absolute, and the output is sanitised on GitHub's side — the styling for headings, code blocks and tables is then written once for the dark theme.

Degrading honestly when the API is gone

If a request fails the badges simply do not render and the page still works. The failure modes are kept apart on purpose: a 404 means the repository genuinely has no README, anything else means it could not be fetched. Collapsing the two would make the page claim a documented project has no documentation whenever the rate limit ran out.

A data driven project registry

Every project is one record in a single file — title, summary, tags, category, accent colour, and a written description used when there is no README. Category filters and their counts are derived from that list, so an empty category disappears and a new one appears without touching the component. Projects with no public repository are supported by leaving the repo field out.

One palette, not per-brand colours

Card covers are generated from a gradient rather than screenshots, and technology logos are tinted to the site's own accent instead of their brand colours. Hue varies a little by category while saturation and lightness stay fixed, which is what lets nineteen cards read as one set.

A full screen overlay that swallowed every click

The animated particle layer is position fixed at full width and height, so it covered the whole page and absorbed every click beneath it — the category filters did nothing, and the social links on the home page had never worked. Adding pointer-events: none to that layer fixed all of them at once. It also explains why testing by calling .click() in the console is not enough: that path skips hit testing entirely and reports success on a button no user can reach.
